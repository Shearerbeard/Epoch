Three Integration Surfaces

What panels A, B, and C from the failure atlas each demand of Epoch's public types — model lines in Haskell-like syntax, integration surface in post-redesign Rust (AFIT, &self, typed stream ids, split version types). Every type shown is a proposal, not shipped API; see the ADRs for status. Ends with the control-plane answer: why postgres advisory locks replace the Datomic transactor we don't have.

Shared foundation

The core every option builds on

These types make the ADR 0001-0005 decisions concrete and are common to all three panels — they replace VersionedEventRepositoryWithStreams<'a, E, Err> outright.

model · haskell-likedata ExpectedVersion v = Any | NoStream | StreamExists | Exact v   -- write-side assertion
data StreamVersion   v = Empty | At v                              -- read-side observation
data AppendError v e  = Conflict (VersionDiff v) | Backend e        -- branch once, typed

class StreamId s where                                             -- the two-way contract
  streamKey :: s -> Text
  parseKey  :: Text -> Either StreamIdError s

load   :: streams -> s -> IO ([e], StreamVersion v)
append :: streams -> s -> ExpectedVersion v -> [e]
       -> IO (Either (AppendError v err) (StreamVersion v))
integration surface · rust// epoch::stream — the two-way id contract (replaces WithFineGrainedStreamId + StreamIdFromEvent)
pub trait StreamId: Sized + Send + Sync {
    fn stream_key(&self) -> Cow<'_, str>;
    fn parse_key(key: &str) -> Result<Self, StreamIdError>;
}
// blanket impl for String keeps tests terse

// epoch::version — one enum did two jobs; now split
pub enum ExpectedVersion<V> { Any, NoStream, StreamExists, Exact(V) }
pub enum StreamVersion<V>   { Empty, At(V) }
pub enum AppendError<V, E>  { Conflict(VersionDiff<V>), Backend(E) }

// epoch::repository — AFIT, no lifetime, no &mut, no async_trait
#[trait_variant::make(Send)]
pub trait EventStreams<E: Event> {
    type Id: StreamId;
    type Version: Copy + Ord + Send + Sync;
    type Err: std::error::Error + Send + Sync;

    async fn load(&self, id: &Self::Id)
        -> Result<(Vec<E>, StreamVersion<Self::Version>), Self::Err>;
    async fn load_from(&self, id: &Self::Id, from: Self::Version)
        -> Result<(Vec<E>, StreamVersion<Self::Version>), Self::Err>;
    async fn append(&self, id: &Self::Id,
                    expected: ExpectedVersion<Self::Version>, events: &[E])
        -> Result<StreamVersion<Self::Version>, AppendError<Self::Version, Self::Err>>;
}

Chore-lottery's bound collapses from the HRTB block to KS: EventStreams<KidEvent, Id = KidStreamId> — the eight error-mapping blocks become one match on AppendError per operation.

Panel A · app coordinator

A — no new Epoch surface; the app owns the gap

model · haskell-like-- ordering IS the design: reserve on the authority stream, then accept.
draw :: Kid -> App DrawOutcome
draw kid = do
  (chore, vc) <- load chores card
  reserve     <- append chores card (Exact vc) [Assigned kid]   -- ① atomic alone
  -- ✂ orphan window: crash here leaves the card assigned, kid untouched
  accept      <- append kids kid (Exact vk) [DrewChore card]    -- ② atomic alone
  pure (Drawn ...)
-- compensation (parent return frees the orphan) is domain code, not library code

Epoch ships nothing beyond the foundation. The ledger's F2/F3/F4 stay real and stay the application's to repair. This is the fallback shape for any backend that can't do C — and after the foundation lands it costs perhaps a third of today's coordinator bulk.

Panel B · saga / event router

B — Epoch grows a delivery control plane

The saga itself is trivial; the honest cost is everything around it. Epoch would need a consumer-offset feed over the global log — this is the piece Fmodel delegates to fstore-sql and EvidentDB delegates to Kafka.

model · haskell-likereact :: UpstreamEvent -> [DownstreamCmd]        -- pure, stateless, dumb pipe

runner :: Feed -> App ()
runner feed = forever $ do
  batch <- poll feed group                       -- at-least-once
  traverse_ (execute . react) batch              -- execute must be idempotent!
  ack feed group (cursor batch)                  -- nack ⇒ redelivery
integration surface · rust (new epoch items)// epoch::saga — the pure pipe (mirrors Fmodel/Calderwood React)
pub struct Saga<Ar, A> { pub react: fn(&Ar) -> Vec<A> }

// epoch::feed — NEW capability: ordered, resumable delivery of committed events
#[trait_variant::make(Send)]
pub trait EventFeed<E: Event> {
    type Cursor: Copy + Ord + Send + Sync;        // pg: global_sequence
    type Err: std::error::Error + Send + Sync;

    async fn poll(&self, group: &ConsumerGroup, after: Option<Self::Cursor>, max: usize)
        -> Result<Vec<Delivery<E, Self::Cursor>>, Self::Err>;
    async fn ack(&self, group: &ConsumerGroup, upto: Self::Cursor)
        -> Result<(), Self::Err>;                 // no ack ⇒ redelivered next poll
}

// epoch::saga::runner — owns the retry loop so domain code never sees delivery
pub struct SagaRunner<F, Exec> { feed: F, exec: Exec, group: ConsumerGroup }
Control plane, no transactor edition Postgres already assigns global_sequence at commit; the feed is a consumer_offsets(group, last_seq) table plus SELECT … WHERE global_sequence > $1 ORDER BY global_sequence, with LISTEN/NOTIFY as a latency optimization over polling. At-least-once falls out; idempotent command execution becomes a domain obligation — for chore-lottery that's a new obligation the current deciders only partly meet (AlreadyHolds covers draw, nothing covers double-MarkReturned).
Panel C · atomic multi-stream batch

C — one capability trait; the window stops existing

The wrinkle EvidentDB never faces: it has one CloudEvent type, we have KidEvent and ChoreEvent. Two honest answers: the Fmodel answer (a consumer-side Sum event and a combined decider — one repository, problem dissolved) or the store answer (heterogeneous writes erased at the batch boundary, where events become rows anyway). The skeleton below is the store answer, because it keeps chore-lottery's aggregates separate — but note the Fmodel answer needs zero new Epoch surface.

model · haskell-like-- the whole draw is one conditional commit; F2/F3/F4 are unrepresentable
draw :: Kid -> Card -> App DrawOutcome
draw kid card = transact store
  [ StreamAt (choreKey card) vc          -- constraints may cover streams…
  , StreamAt (kidKey kid)    vk ]        -- …the batch also writes, or not
  [ Write (choreKey card) [Assigned kid ...]
  , Write (kidKey kid)    [DrewChore card ...] ]
-- transact :: Store -> [Constraint v] -> [Write] -> IO (Either (BatchConflict v) v)
integration surface · rust (new epoch items)// epoch::batch — constraint vocabulary, straight from EvidentDB minus Subject
pub enum BatchConstraint<V> {
    StreamExists(StreamKey),
    StreamDoesNotExist(StreamKey),
    StreamAt(StreamKey, ExpectedVersion<V>),
}

// A write is type-erased AT THE BOUNDARY: events serialize to rows anyway,
// so heterogeneity (KidEvent + ChoreEvent) costs nothing here.
pub struct Batch<V> { writes: Vec<ErasedWrite>, constraints: Vec<BatchConstraint<V>> }

impl<V> Batch<V> {
    // typed on the way in; the repo contributes stream_type + serialization
    pub fn write<E>(&mut self, streams: &impl EventStreams<E, Version = V>,
                    id: &impl StreamId, expected: ExpectedVersion<V>, events: &[E])
        -> Result<(), EncodeError>
    where E: Event + Serialize;
}

// the capability: postgres + in_memory implement it; ESDB simply doesn't.
// the type system, not documentation, tells you which panel a backend supports.
#[trait_variant::make(Send)]
pub trait AtomicStreams {
    type Version: Copy + Ord + Send + Sync;
    type Err: std::error::Error + Send + Sync;

    async fn transact(&self, batch: Batch<Self::Version>)
        -> Result<Committed<Self::Version>, BatchError<Self::Version, Self::Err>>;
}

pub enum BatchError<V, E> {
    Conflict { violated: BatchConstraint<V>, actual: StreamVersion<V> },
    Backend(E),
}
The control plane

Coordination without a transactor

Datomic and EvidentDB serialize by construction: one writer per database, every batch through one funnel. We don't have that — and don't need it, because the funnel's only job is mutual exclusion over the streams a batch touches, and postgres sells that à la carte: 

pg transact — the whole control planeBEGIN;
-- ① lock every touched stream key, IN SORTED ORDER (sorted ⇒ no deadlock cycles)
SELECT pg_advisory_xact_lock(hashtext(k))
  FROM unnest($sorted_stream_keys) AS k;
-- ② evaluate every BatchConstraint against MAX(sequence) per stream — a consistent
--    snapshot, because ① serialized us against every writer that could move them
-- ③ any violation ⇒ ROLLBACK ⇒ BatchError::Conflict { violated, actual }
-- ④ insert all rows; global_sequence (bigserial) orders the committed log
COMMIT;   -- locks release with the transaction, even on async cancellation

This is strictly better than the single writer for our shape: batches touching disjoint streams commit in parallel (the transactor would queue them), while batches contending on a stream serialize exactly as EvidentDB's funnel would. What we give up is a database-wide basis_revision — our constraints are per-stream, not whole-database — which is precisely why BatchConstraint stays a per-stream vocabulary. The existing single-stream append is the degenerate one-write batch; it already takes this exact lock. In-memory implements transact with its one store mutex (trivially serial); ESDB doesn't implement it, and the missing impl is the documentation.
