Two-Stream Failure Atlas

Every way a draw or return can die between the kid stream and the chore stream, what state each death leaves behind, and who repairs it. Companion to the Fmodel / EvidentDB research: the open question is where the cross-stream invariant should live — app coordinator (today), saga/router, or atomic multi-stream batch. The saga and batch designs shown here are proposals, not shipped API.

The invariant

One card, one kid — with no transaction that spans both facts

A draw must make two facts true in two different event streams: the chore stream records the card Assigned to the kid, and the kid stream records the kid accepting it (DrewChore). Epoch gives one primitive: a version-checked append to a single stream. Nothing spans both. Chore-lottery's answer today: order the writes so the failure modes are benign — chore-first on draw, kid-first on return — and give every gap a named repair path. This document draws each gap.

Figure 1 · the draw

Chore-first draw, with its three failure windows

The orphan is deliberately not repaired by the draw path. The kid remains Idle, can draw a different card, and the stuck card shows up in chore-lottery's parent-facing view of long-held cards; a parent return is the compensation. reconcile only handles the inverse retry: kid stream says Working, so re-read the card and hand back AlreadyHolds instead of drawing twice.

Caveat: the in-memory OCC hole Every one of these guarantees rests on the version check. The in-memory backend tracks position = len − 1, so an empty stream and a one-event stream are both "version 0" — two racing single-event appends at Exact(0) both succeed. Chore-lottery's deciders emit single-event batches, which means the race tests that validated this atlas in memory were partly testing an OCC that wasn't there. The postgres backend (1-based sequence, NoStream for empty) is correct. Unifying version semantics on the postgres model is a prerequisite for trusting any multi-stream story.
Figure 3 · the actual question

Three homes for the cross-stream invariant

The eight repeated error-mapping blocks and the two hand-ordered appends are symptoms. The disease is that somebody has to own the in-between state (the orphan), and today that somebody is the application. The three candidate designs differ in exactly one thing: where the atomicity boundary sits, and therefore who carries the gap.

Research findings · fmodel (fraktalio)

Fmodel: combine when invariants are shared, saga when they aren't

Fmodel ships no two-stream primitive. It ships a design axis with two poles, and a rule for choosing (Dugalic, fmodel discussions #37 and #334):

  1. Decider::combine — the strong pole. A monoid: Decider<C1,S1,E1> + Decider<C2,S2,E2> → Decider<Sum<C1,C2>, (S1,S2), Sum<E1,E2>>. The combined decider handles a command in one fetch → decide → save cycle; if the repository commits in one transaction (their sqlx demo does, even across decider_id streams), the two former aggregates become one consistency boundary. Rule: combine only deciders that share an invariant.
  2. Saga — the eventual pole. Deliberately a stateless dumb pipe: react: Fn(&Event) → Vec<Command>. All retry and at-least-once machinery lives in the event-streaming adapter (their fstore-sql: a Postgres poll stream with ack/nack offsets), never in the saga. Stateful process managers were removed on purpose — a workflow with state should be its own Decider.
  3. Verdict for this atlas: "one card, one kid" is a shared invariant, so Fmodel's answer to Figures 1–2 is blunt: the kid and chore deciders belong in one consistency boundary for the draw — panel C — not in a hand-ordered panel A. Compensation-by-parent-return would remain domain code either way.
Research findings · evidentdb (calderwood)

EvidentDB: the multi-stream atomic batch is real; the "event router" description is not

  1. Confirmed — panel C exists in the wild. One transactBatch carries events for multiple streams plus a list of BatchConstraints — StreamExists / StreamDoesNotExist / StreamMaxRevision, and the same three over Subject and SubjectOnStream — all evaluated against one database-wide basis_revision. The whole batch commits or the whole batch rejects. Constraints may reference streams the batch doesn't even write.
  2. The "event router" description is inaccurate. Cross-stream automation in Calderwood's model is an application-side React (AR) → List<A> function (same shape as Fmodel's saga), eventual by nature. The only literal router in the codebase is Kafka topic plumbing. The database's own contribution to multi-stream use cases is precisely the atomic constrained batch.
  3. The cost that bought it: a Datomic-style single writer per database (Kafka Streams transactor, one partition per database log). Write throughput caps at the database; scaling out means sharding databases and falling back to sagas across them.
  4. Status: alpha, dormant since Jan 2024, canonical repo deleted (a full mirror survives), Apache-2.0. A design source, not a dependency.
Convergent conclusion Both reference designs agree: there is no missing "two-stream coordinator" abstraction. Shared invariant → widen the atomic boundary (combine / constrained batch, panel C). No shared invariant → stateless event-to-command pipe with at-least-once delivery (panel B), retries owned by infrastructure. Panel A — today's hand-rolled ordering — is what you build when the store can't do C and you won't run B. Epoch's postgres backend sits on a store that can do C in one transaction with per-stream advisory locks; ESDB genuinely cannot. That makes the honest library shape a capability split: a batch-append trait postgres implements and ESDB doesn't — with EvidentDB's BatchConstraint vocabulary (minus Subject) as the proven starting point for its expected-version language.
