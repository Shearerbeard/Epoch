Saga & Atomic Batch from the API

Producer-side Rust for eight scenarios: what an axum handler would write under panel B (saga + feed) and panel C (atomic batch). Every API shown here is proposed, not shipped; see the ADRs for status. Internals glossed; the shape of the call is the point. Shared setup assumed throughout:

struct App {
    store:  PgEventStore,                      // implements AtomicStreams + EventFeed
    kids:   PgStreams<KidEvent>,   chores: PgStreams<ChoreEvent>,
    users:  PgStreams<UserEvent>,  trucks: PgStreams<TruckEvent>,
    // every PgStreams is a typed view over the same store; load() returns (events, StreamVersion)
}
// fold(events) → state; Decider::decide(&state, &cmd) → Result<Vec<E>, DomainErr> — glossed below
scenario 1

CUnique bounds without a read model — the claim stream

"Username must be unique" is set validation: a single-entity write gated by a multi-entity fact. Don't consult a read model in the decide path at all — make the fact a stream, so it has an OCC handle. One claim stream per claimed value; NoStream is the uniqueness check.

// POST /users { email }
async fn register(State(app): State<App>, Json(req): Json<RegisterReq>) -> ApiResult {
    let user = UserId::new();
    let mut batch = Batch::new();

    // the uniqueness invariant IS this line: first writer wins, forever
    batch.write(&app.email_claims, &EmailClaimId::from(&req.email),
                ExpectedVersion::NoStream, &[EmailClaimed { user }])?;
    batch.write(&app.users, &UserStreamId::from(user),
                ExpectedVersion::NoStream, &[UserRegistered { email: req.email }])?;

    match app.store.transact(batch).await {
        Ok(_) => Ok(Json(user)),
        Err(BatchError::Conflict { violated, .. }) => Err(ApiError::conflict("email taken")),
        Err(BatchError::Backend(e)) => Err(ApiError::internal(e)),
    }
}

Consistency: strong. No stale window exists because nothing was read — the constraint carries the whole invariant. This is the pattern scenario 8 falls back to when versioned ctx is too coarse.

scenario 2

CKids / chores: chore-lottery's draw

// POST /kids/:kid/draw
async fn draw(State(app): State<App>, Path(kid): Path<KidId>) -> ApiResult {
    let (kid_ev, v_kid)     = app.kids.load(&KidStreamId::from(kid)).await?;
    let kid_state           = fold(kid_ev);            // gate: Idle, else AlreadyHolds path
    let card                = app.pool.select(roll)?;  // read model picks the candidate
    let (chore_ev, v_chore) = app.chores.load(&ChoreStreamId::from(card)).await?;

    let assigned = ChoreDecider::decide(&fold(chore_ev), &Assign { kid, .. })?;
    let drew     = KidDecider::decide(&kid_state, &DrawChore { card, .. })?;

    let mut batch = Batch::new();
    batch.write(&app.chores, &card, v_chore.into_exact(), &assigned)?;
    batch.write(&app.kids,   &kid,  v_kid.into_exact(),   &drew)?;

    match app.store.transact(batch).await {
        Ok(committed) => Ok(Json(DrawOutcome::from(committed))),
        Err(BatchError::Conflict { .. }) => Err(ApiError::retry_after_reload()),  // old F1; F2–F4 gone
        Err(BatchError::Backend(e)) => Err(ApiError::internal(e)),
    }
}

The pool read model still selects the candidate (stale is fine — the batch is the truth check). The whole coordinator, reconcile machinery aside, becomes this handler.

scenario 3

CTrucker-buddy — write one stream, constrain another

User creation requires the assigned truck to exist at commit time. The batch never writes the truck stream — it only pins it. This is the EvidentDB move: constraints range over streams the batch doesn't touch.

// POST /users { name, truck_id }
async fn create_user(State(app): State<App>, Json(req): Json<CreateUser>) -> ApiResult {
    let user = UserId::new();
    let mut batch = Batch::new();

    // existence pin: locked + checked in the same tx as the write — a truck
    // decommissioned concurrently makes this batch CONFLICT, not silently succeed
    batch.constrain(BatchConstraint::StreamExists(app.trucks.key(&req.truck_id)));

    batch.write(&app.users, &UserStreamId::from(user), ExpectedVersion::NoStream,
                &[UserCreated { name: req.name, truck: req.truck_id }])?;

    respond(app.store.transact(batch).await)
}
Sharper variant StreamExists asserts "was ever created." If the invariant is "exists and is currently in service," existence isn't enough — either constrain StreamAt(trucks.key(id), Exact(v)) with the version you validated the truck's state at (see scenario 8), or write a marker event to the truck stream and let its decider reject when decommissioned. Choose by whether the truck aggregate should know about assignments.
scenario 4

CGroup vs individual — the parent stream as OCC anchor

"users vs user/<id>" generalized: any invariant over a set (fleet cap, members per family, open cards per board) gets a stream of its own — the group parent — so the group state has a version you can hold. The category index (load(None) today) is for reads; it is not an OCC handle.

// POST /companies/:id/trucks — cap: max 5 active trucks per company
async fn register_truck(State(app): State<App>, Path(company): Path<CompanyId>) -> ApiResult {
    let (fleet_ev, v_fleet) = app.companies.load(&CompanyStreamId::from(company)).await?;
    let truck = TruckId::new();

    // the CAP lives in the company decider — group state is first-class aggregate state
    let fleet_events = CompanyDecider::decide(&fold(fleet_ev),
                            &RegisterTruck { truck })?;   // Err(FleetFull) at 5

    let mut batch = Batch::new();
    batch.write(&app.companies, &company, v_fleet.into_exact(), &fleet_events)?;
    batch.write(&app.trucks, &truck, ExpectedVersion::NoStream,
                &[TruckRegistered { company }])?;
    respond(app.store.transact(batch).await)   // two racers at 4/5 trucks: exactly one wins
}

Rule of thumb: a "many-stream" invariant is a smell that a parent aggregate is missing. Scenario 1's claim stream is this pattern at its smallest (a parent per claimed value); this is the same pattern with real state.

scenario 5

CBCanonical: account transfer — both primitives, honestly compared

// POST /transfers { from, to, amount } — panel C: both-or-neither, now
let (a_ev, v_a) = app.accounts.load(&from).await?;
let (b_ev, v_b) = app.accounts.load(&to).await?;
let debit  = AccountDecider::decide(&fold(a_ev), &Debit  { amount, transfer })?;  // Err(Insufficient)
let credit = AccountDecider::decide(&fold(b_ev), &Credit { amount, transfer })?;

let mut batch = Batch::new();
batch.write(&app.accounts, &from, v_a.into_exact(), &debit)?;
batch.write(&app.accounts, &to,   v_b.into_exact(), &credit)?;
app.store.transact(batch).await   // money is conserved by the transaction
// same domain, panel B: the transfer is its own aggregate; the saga moves it
// POST /transfers → one plain append; the API returns 202 Accepted
app.transfers.append(&transfer_id, ExpectedVersion::NoStream,
                     &[TransferRequested { from, to, amount }]).await?;

// registered once at startup — pure routing, no state, no I/O:
fn react(ev: &AppEvent) -> Vec<AppCommand> {
    match ev {
        TransferRequested { from, amount, transfer, .. }
            => vec![DebitSender    { account: *from, amount: *amount, transfer: *transfer }],
        SenderDebited     { to, amount, transfer, .. }
            => vec![CreditRecipient{ account: *to,   amount: *amount, transfer: *transfer }],
        DebitRejected     { transfer, .. }                       // insufficient funds
            => vec![FailTransfer   { transfer: *transfer }],
        CreditRejected    { transfer, from, amount, .. }         // account closed mid-flight
            => vec![RefundSender   { account: *from, amount: *amount, transfer: *transfer }],
        _ => vec![],
    }
}
// SagaRunner::new(app.store.feed(), executor).run()  — at-least-once; every command idempotent by transfer id

C: one handler, conservation by transaction, nothing to compensate. B: 202-style API, per-step aggregates, and the compensations (RefundSender) are honest domain events — which is exactly what you want when the two accounts live in different stores or services. Same domain, different deployment truth.

scenario 6

C⚔Antagonistic: the flash sale that wants to oversell

Three units of stock, five hundred concurrent buyers, a client that retries on any non-200, and a load balancer that duplicates requests. The design that survives this is the one where correctness never depends on politeness.

// POST /items/:id/purchase  (idempotency_key from the client)
async fn purchase(State(app): State<App>, Path(item): Path<ItemId>,
                  Json(req): Json<PurchaseReq>) -> ApiResult {
    let (ev, v) = app.items.load(&item).await?;
    let events  = ItemDecider::decide(&fold(ev),
                     &Purchase { buyer: req.buyer, key: req.idempotency_key })?;
                     // state knows remaining stock AND seen keys → Err(SoldOut) / Ok(already-yours)

    let mut batch = Batch::new();
    batch.write(&app.items, &item, v.into_exact(), &events)?;
    // claim stream makes the duplicate-request case structural, not just state-checked:
    batch.write(&app.purchase_claims, &ClaimId::from(req.idempotency_key),
                ExpectedVersion::NoStream, &[PurchaseClaimed { item }])?;

    match app.store.transact(batch).await {
        Ok(_) => Ok(Json(Purchased)),
        Err(BatchError::Conflict { violated: StreamDoesNotExist(_), .. })
            => Ok(Json(Purchased)),                     // duplicate of OUR OWN win: 200, idempotent
        Err(BatchError::Conflict { .. }) => Err(ApiError::retry_after_reload()),  // lost the race
        Err(BatchError::Backend(e)) => Err(ApiError::internal(e)),
    }
}
Why this is the antagonistic case, and why it matters here Under the current in-memory backend this exact code oversells: single-event appends at Exact(0) both succeed (the len − 1 off-by-one), so 500 buyers × 1-event batches = no OCC at all. The antagonist doesn't need to be clever — the arithmetic is on their side. This scenario becomes the spec test that pins the unified version semantics.
scenario 7

COCC held across streams — blocking, then a typed loss

Two batches with overlapping write-sets, fired concurrently. This is the smoke-test shape, a consumer-shaped round-trip, and the clearest picture of what the advisory locks actually do: blocking is brief and invisible; conflict is typed and yours.

// batch_1 writes {alice, bob};  batch_2 writes {bob, carol} — same instant
let (r1, r2) = tokio::join!(
    app.store.transact(batch_over(&[&alice, &bob],  v_a1, v_b1)),
    app.store.transact(batch_over(&[&bob,  &carol], v_b2, v_c1)),
);

// timeline (locks taken in sorted key order: alice < bob < carol):
//   t0  b1: lock(alice) ✓  lock(bob) ✓          b2: lock(bob) …BLOCKS (held by b1)
//   t1  b1: constraints hold → insert → COMMIT  (bob is now at n+1; locks release)
//   t2  b2: lock(bob) ✓ lock(carol) ✓ → check Exact(n) vs MAX(seq)=n+1 → ROLLBACK
//   t3  b2 returns Err(Conflict { violated: StreamAt(bob, Exact(n)), actual: At(n+1) })

assert!(r1.is_ok());
assert!(matches!(r2, Err(BatchError::Conflict { .. })));   // exactly one winner, deterministically

The blocking window is the length of b1's insert — milliseconds, bounded, deadlock-free by sorted acquisition. No caller ever observes "blocked" as a state; they observe either Committed or Conflict-with-evidence. Batches touching disjoint streams (alice+bob vs carol+dave) never block each other at all — the parallelism Datomic's funnel gives up.

scenario 8

⚠The injected-context hazard and its two disarms

Stated precisely: DeciderWithContext::decide(ctx, state, cmd) gives ctx no OCC handle. The append's version check covers only the target stream — the store verifies the data you fold, never the data you inject. Any decision that ctx can veto is being made against unverifiable staleness:

// TODAY — the hazard in the open
let users_view = app.users_view.snapshot();          // built from the users category… when?
let events = UserDecider::decide(&users_view, &state, &Register { email })?;
                                  // ctx says email is free — as of an unknowable moment
app.users.append(&user, v.into_exact(), &events).await?;
   // OCC checks user/<id> only. A racing Register on a DIFFERENT user stream
   // invalidated ctx and nothing here can ever notice. Commit succeeds; invariant broken.

Two disarms, by weight of the invariant:

// Disarm A — give ctx the OCC handle it's missing: a basis the batch re-asserts.
pub struct Versioned<C, V> {
    pub value: C,
    pub basis: Vec<(StreamKey, StreamVersion<V>)>,   // the streams this ctx was read AT
}

let fleet: Versioned<FleetView, _> = app.fleet_view.load_versioned(&company).await?;
let events = TruckDecider::decide(&fleet.value, &state, &cmd)?;

let mut batch = Batch::new();
batch.constrain_basis(&fleet.basis);   // StreamAt(k, Exact(v)) for every source stream
batch.write(&app.trucks, &truck, v.into_exact(), &events)?;
app.store.transact(batch).await       // stale ctx is now a typed Conflict, not a silent lie

Disarm A is honest but has a scaling cliff: if ctx derives from a whole category ("all users"), the basis is a high-water mark over it, and any unrelated user registration conflicts you — correct, but hot. That cliff is the signal the invariant was never really "about the whole category": shrink the basis by restructuring — scenario 1's claim stream (basis = one claim) or scenario 4's parent aggregate (basis = one group stream). Then the constrained streams are exactly the invariant's true participants and contention matches real contention.

The resulting rule for Epoch's docs ctx is for enrichment (ids, clocks, config, data that shapes events but never gates acceptance). The moment ctx can turn an accept into a reject, it must be either constrained (Versioned + basis, disarm A) or reified into streams (claim / parent aggregate, disarm B). Free-floating veto-ctx is the one shape we now know to be unsound.
