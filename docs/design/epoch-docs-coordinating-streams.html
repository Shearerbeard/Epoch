Coordinating Across Streams

Most commands touch one stream. This guide is about the ones that don't — and the two tools Epoch gives you for them: the atomic batch and the saga.

Northstar draft This guide describes the intended shape of the batch and saga APIs; neither has shipped yet.

The problem

In Epoch, every aggregate gets its own event stream, and every append is protected by an optimistic version check: your write lands only if the stream is where you left it. That single guarantee carries most applications a long way.

Then one day a command needs to change two facts in two streams. A player draws a card: the card must become taken and the player must become holding it. A transfer moves money: one account debits, another credits. A signup claims a username that must be unique across all users. Two appends means two version checks — and a gap between them where a crash or a concurrent writer leaves your system half-changed.

You could hand-order the appends and write repair code for every gap. Epoch's earlier consumers did exactly that, and it works — but it's the most delicate code in the application, and it's the same delicate code every time. This guide describes the two patterns Epoch is adopting to replace that delicate code.

Tool one: the atomic batch — when facts must change together

If the facts belong to one invariant — the system is simply wrong if one changes without the other — put both writes in one Batch and commit it with transact. The whole batch lands or none of it does, and every version check in it is evaluated at the same instant: 

let mut batch = Batch::new();
batch.write(&cards,   &card,   card_version.into_exact(),   &[CardTaken { by: player }])?;
batch.write(&players, &player, player_version.into_exact(), &[CardDrawn { card }])?;

match store.transact(batch).await {
    Ok(committed) => { /* both facts are true */ }
    Err(BatchError::Conflict { violated, actual }) => { /* neither is; reload and retry */ }
    Err(BatchError::Backend(e)) => { /* infrastructure */ }
}

A batch can also pin streams it never writes. Creating a user who must reference an existing truck? Constrain the truck's stream and write only the user's — if the truck is deleted concurrently, your batch conflicts instead of committing a dangling reference: 

batch.constrain(BatchConstraint::StreamExists(trucks.key(&truck_id)));

Uniqueness works the same way. Give each claimed value its own tiny stream and assert it doesn't exist yet — the first writer wins, and there's no read model to go stale: 

batch.write(&email_claims, &claim_for(&email), ExpectedVersion::NoStream, &[Claimed { user }])?;

There is nothing to clean up after a batch. No compensation events, no repair jobs, no "what if we crashed in the middle" — the middle doesn't exist.

Not every backend can do this transact lives on the AtomicStreams trait, which a backend implements only if its store can commit several streams under one consistency check. The PostgreSQL and in-memory backends are slated to implement it. EventStoreDB cannot, and doesn't pretend to — if your backend lacks AtomicStreams, the compiler tells you, and you fall back to ordered single appends with explicit repair paths.

Tool two: the saga — when one thing follows from another

Not every relationship is an invariant. Often the second write isn't part of the command at all — it's a consequence. When an order ships, the customer gets an email. When a card is taken, the external task tracker gets updated. When a transfer is requested, a debit should be attempted. These are reactions, and reactions want to happen eventually and reliably, not atomically.

A saga is a pure routing function — an event in, commands out, no state, no I/O: 

fn react(event: &AppEvent) -> Vec<AppCommand> {
    match event {
        TransferRequested { from, amount, .. } => vec![DebitSender { account: *from, amount: *amount }],
        SenderDebited { to, amount, .. }       => vec![CreditRecipient { account: *to, amount: *amount }],
        CreditRejected { from, amount, .. }    => vec![RefundSender { account: *from, amount: *amount }],
        _ => vec![],
    }
}

You hand that function to a SagaRunner, and Epoch does the rest: it follows the store's committed event log through an EventFeed, remembers how far your saga has read, delivers each event at least once, and re-delivers anything whose handling failed — through crashes, restarts, and redeploys. Your API handler just appends the triggering event and returns; the saga carries the workflow from there.

The one thing the saga asks of you "At least once" means your command handling must tolerate a repeat. Design each command so running it twice is harmless — key it by an id the retry shares (the transfer id, the order id), and let your decider answer a duplicate with "already done" instead of doing it again. If a reaction can't be made repeat-safe, it isn't ready to be a saga.

Choosing

One question does most of the work: if the second write never happened, would the first one be a lie?

  • Yes → it's an invariant. Use a batch. A card marked taken with no holder is a lie; a debit with no credit is a lie.
  • No → it's a reaction. Use a saga. An order with the confirmation email still pending isn't a lie — it's just not finished yet.

The two compose naturally, and most real features use both: the command commits its invariant as one batch, and sagas fan the consequences out from the committed events. In the card game: the draw is a batch (card + player move together); syncing the external task board, notifying the parent's phone, and refreshing the leaderboard are three sagas reading the same log. If you're staring at a transfer-like workflow that spans stores or services, the batch is off the table — model each step as its own aggregate and let a saga walk the chain, with explicit compensation events for the steps that can be refused.
